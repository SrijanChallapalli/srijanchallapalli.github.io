The problem

I wanted to know what "durable" actually costs.

Every backend leans on a database, but "it's persisted" hides an enormous amount of engineering: how does a write survive a crash mid-flush? Why are writes fast when disks are slow at random I/O? How do you find a key without scanning every file? The best way to stop treating those as magic is to build the thing.

So I'm implementing the log-structured merge tree — the design behind RocksDB and LevelDB — from scratch in Rust, deliberately without a storage library, to feel every durability and performance tradeoff directly.

The system

Turn slow random writes into fast sequential ones.

The core idea: never do random writes to disk. Every PUT is first appended to a write-ahead log (sequential, durable) and inserted into an in-memory memtable. When the memtable fills, it's flushed as an immutable, sorted SSTable on disk. Reads check the memtable, then newest-to-oldest SSTables, using per-table bloom filters to skip files that can't contain the key. A background compaction thread merges SSTables to bound read amplification and reclaim space from overwritten and deleted keys.

On startup, the engine replays the WAL to rebuild any memtable state that hadn't been flushed — so an unexpected crash costs nothing that was acknowledged. The diagram above traces the full write path.

Technical challenges

The genuinely hard parts.

01

Durability & crash recovery

Getting the WAL ordering right — fsync before acknowledging a write, and replaying the log on startup — so the engine recovers to a consistent state no matter when the process dies. Verified with fault injection.

02

Concurrent compaction

Compaction runs on a background thread while reads and writes continue. Coordinating that with Arc/Mutex and channels — without blocking the write path or exposing a half-merged view — is the trickiest concurrency in the project.

03

Bounding read amplification

Without compaction, a read may touch every SSTable ever written. Bloom filters cut most of those out, and the compaction strategy keeps the number of tables a read must consult under control.

04

Measuring, not guessing

Throughput and tail latency are benchmarked with Criterion and profiled with Linux perf, so design changes are judged by numbers rather than intuition.

Engineering decisions

Choices, and what they cost.

01

LSM tree over a B-tree

Why I chose it
Write-optimized: turns random writes into sequential appends, which is how modern write-heavy stores are built.
Alternative considered
A B-tree / B+-tree with in-place updates.
Tradeoff
Reads can touch multiple SSTables and compaction adds write amplification — paid down with bloom filters and merging.
02

WAL with fsync-before-ack

Why I chose it
A write is only "done" once it's durable — anything acknowledged must survive a crash.
Alternative considered
Buffered writes acknowledged before they hit disk.
Tradeoff
Higher per-write latency from the sync, in exchange for a correctness guarantee I can actually stand behind.
03

Rust for the implementation

Why I chose it
Memory safety without a garbage collector, and a type system that makes the concurrency in compaction tractable.
Alternative considered
C++ for raw control, or Go for simpler concurrency.
Tradeoff
A steeper borrow-checker learning curve, repaid by catching data races at compile time.

Result

Where it stands.

The engine currently implements the full write path — WAL, memtable, SSTable flush, bloom filters, and background compaction — with WAL-replay crash recovery and a Criterion benchmark harness. Ongoing work is on compaction strategy, richer fault-injection tests, and profiling read/write amplification under load. More than a finished product, it's the fastest way I've found to genuinely understand how a database keeps its promises.
