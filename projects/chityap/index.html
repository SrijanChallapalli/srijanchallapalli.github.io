The problem

Social apps optimize for strangers. This one optimizes for close friends.

Mainstream social apps reward reach: algorithmic feeds, public metrics, and infinite audiences. That's the wrong shape for staying accountable to the handful of people who actually know you. Chityap is built for small, closed friend groups — a strictly chronological feed, daily challenges, and no vanity metrics — so posting stays honest and low-pressure.

Doing that well is deceptively hard: it needs realtime updates across several independent data channels, tight privacy guarantees at the database level, and a native client that feels instant even on a flaky connection.

The system

A native SwiftUI client over a realtime Postgres backend.

The client is a layered SwiftUI app organized across 12 API modules, with boundaries enforced by architecture tests so the UI can't reach past its data layer. The backend is Supabase/Postgres, backed by roughly 180 SQL migrations and 17 feed-path indexes, with row-level security as the primary privacy boundary.

Technical challenges

The genuinely hard parts.

01

Four-channel realtime fan-in

Feed, notifications, friendships, and requests each stream independently. The client merges them into consistent view state and reconnects cleanly when the app returns to the foreground — without duplicating or dropping events.

02

Privacy as a database guarantee

Row-level security policies — not app code — decide who can read what. Push notifications go through Postgres SECURITY DEFINER RPCs so a client can trigger a notification without being handed data it shouldn't see.

03

On-device pose rep-counting

An Apple Vision body-pose pipeline counts exercise reps at 15–30 FPS entirely on-device — no network round-trip, no video leaving the phone — which keeps it fast and private.

04

Feels instant on a bad connection

An offline post queue persists failed writes to disk and retries them, and 17 feed-path indexes keep the chronological feed fast as post volume grows toward five figures.

Engineering decisions

Choices, and what they cost.

01

Row-level security as the privacy boundary

Why I chose it
Privacy rules live in one place — the database — so no client bug can leak another group's data.
Alternative considered
Enforcing access control in application/API code.
Tradeoff
Policies are harder to write and test than app-level checks, but they fail closed by default.
02

Native SwiftUI over cross-platform

Why I chose it
Direct access to HealthKit and Vision, and the native feel and performance a social app needs.
Alternative considered
React Native / Flutter for one codebase across platforms.
Tradeoff
iOS-only for now, in exchange for on-device ML and a first-class native UX.
03

On-device Vision, not a server model

Why I chose it
Rep-counting stays private and instant — no video uploaded, no round-trip latency.
Alternative considered
Streaming frames to a server-side pose model.
Tradeoff
Bounded by on-device compute, but far better for privacy, cost, and responsiveness.

Result

A real product in real hands.

Chityap is live in beta with 300+ users who've created nearly 5,000 posts. The codebase spans 140+ Swift files with 100+ unit tests and architecture tests guarding module boundaries — shipped and maintained as a genuine social product rather than a prototype.
